## Primary question

When causal E1 and matched shuffled ES are given an outcome-blind, externally generated return schedule that is prospectively constrained to expose the already-defined hidden-return commit gate, does causal hidden-source assignment produce a different retained physical update pattern and later visible response than the matched shuffled assignment?

The purpose is not to maximize task success. The purpose is to make the registered physical comparison *reachable* while preserving the E1/ES isolation.

## Fixed scientific isolation

The following invariants are mandatory before execution:

1. **Fresh identity and fresh development worlds.** RD005 must use a new deterministic world/schedule generation salt and a disjoint exposed-development seed/world set fixed before implementation results are opened.
2. **Same inherited learner constants.** Hidden eligibility lifetime, lag bounds, plasticity constants, gain/dynamics and native resource guards remain inherited from RD004 unless a later prospective protocol revision is written *before* any RD005 capability execution. No value may be changed in response to RD005 outcomes.
3. **E1/ES event-budget equality.** E1 and ES consume the exact same preregistered hidden-eligibility event identities and the exact same external-return event identities. ES differs only by the deterministic hidden-source assignment permutation.
4. **Outcome-blind return generation.** The external-return schedule may depend on fixed world topology, fixed connection inventory and fixed timing construction, but never reward, route correctness, later task outcome, evaluator truth or observed E1/ES success.

6. **No native-guard rescue.** Existing time/memory/event guards are not raised to obtain a complete result. A guard failure remains incomplete and is preserved.
7. **No behavioral-threshold rescue.** Existing downstream visible-response scoring definitions are not relaxed after execution. Physical update accounting is retained separately from behavioral interpretation.

## Gate-reachability certificate

Before any A/B capability run is opened, each registered external-return event must be mechanically certifiable from construction-only material as follows:

```text
candidate hidden eligibility identity is fixed
external target identity is fixed
return delay lies inside inherited eligibility lag window
assigned hidden source -> external target edge exists
edge is plastic
edge has non-negative initial weight
schedule does not inspect model output or task correctness
```

The certificate is evaluated independently for the causal E1 assignment and the shuffled ES assignment. The *event budget and timing* must be identical across the pair; only source assignment may differ.

If a shuffled assignment makes an event ineligible because the mapped source lacks the required edge, that fact is retained as part of the registered ES physical null rather than repaired after execution. The design must therefore report prospective reachable-event counts for both arms before opening capability.
